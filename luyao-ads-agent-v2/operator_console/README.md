# 陆遥广告运营台 V1.8

这是陆遥广告智能体 V2.1 运行时的独立操作网站，业务规则集仍为 V2.0。顶部“智能补货”只跳转到另一个独立项目，不在广告网站内渲染补货业务。操作页面只展示用户输入、问题提示、Validator 通过后的结果预览和结果下载。

界面采用陆遥绿色品牌系统：桌面端为左侧业务导航、顶部状态栏、浅灰工作区和白色任务卡；关键操作使用品牌绿，问题阻断使用独立警示色。移动端自动收起侧栏并重排表单和处理结果。

访问主次固定如下：用户本人日常使用的主入口是本机 `http://localhost:3001/`，具备上传、报表聚合、方案生成和结果下载；公开演示版只是本地页面底部的“分享演示版”附带链接。远程页面会自动进入 `PUBLIC DEMO`，允许浏览四个入口和操作流程，但关闭真实处理能力。公开网页不接收或保存广告数据。

## 两个独立网站

- 广告系统：`http://localhost:3001/`，只放广告架构设计、SP广告优化、广告数据更新和每周建议；
- 智能补货：`http://localhost:3000/`，由 `/Users/leo/Documents/陆遥智能补货智能体` 独立运行；
- 两个网站使用顶部“广告系统 / 智能补货”切换器互相跳转；不共享规则、阈值、任务状态、上传文件或执行权限。

## 四个入口

1. 广告架构设计：手动逐条添加、编辑或删除最多 10 个 ASIN；更多产品使用一张表格批量导入 → 按 ASIN 分别选词与拆组 → 页面预览 → 下载合并的两表广告架构；
2. SP广告优化：上传/拖拽报表 → 本地 Python 聚合 → 人工点击生成方案 → 页面显示并下载单/多 ASIN 候选优化架构；
3. 更新广告数据：多报表去重并生成 JSON/XLSX 决策包；
4. 查看本周建议：运行每周阈值候选检查，不覆盖当前阈值。

每次任务会在后台生成 `agents_context.json`、Python 工具回执和 Codex 运行回执。上下文逐项记录八层架构、规则、阈值、数据、配置、工具、合同和本次证据的 SHA-256；Validator 独立重建并核对，不能相信网页或模型自报。页面默认不展示这些内部审计内容。广告架构设计支持 `ABA_COLD_START` 人工候选；相关性表和月搜索量表缺失时只生成问题提示，不得伪造匹配方式。

## 固定处理链

```text
网页输入
→ Python 确定性预处理和证据包
→ 服务端构建八层 AGENTS 上下文
→ Codex 读取登记来源生成结构化结论
→ 独立 Validator 核对来源、SHA、工具回执和 Codex 回执
→ 页面预览与最终工作簿
```

Python 生成的新品候选表只是证据，不会直接显示或作为最终下载。最终《新广告设置表》由 Validator 通过后的 `new_product_architecture` 重新生成。SP广告优化遵守同一来源链。

## 最简单的启动方式

双击项目根目录的 `运行广告运营台.command`。首次启动会安装前端依赖并构建页面，之后自动打开：

```text
http://localhost:3001/
```

关闭启动命令的终端窗口会同时停止网页和后台。

## 手动启动

终端 1：

```bash
.venv/bin/python scripts/run_operator_console_backend.py
```

终端 2：

```bash
cd operator_console
npm install
npm run dev -- --port 3001
```

## 数据与安全边界

- 网页可上传 XLSX、XLSM、CSV、TSV；单文件上限 200 MB。原文件只保存到本机 `runtime/operator-uploads/`，不进入 Git，也不会上传到云端。
- 新品尺寸、类型、风格、颜色、材质和场景从 `config/operator_catalog.json` 读取；该属性库必须与新品规则配置保持一致，不在网页中复制业务阈值。
- 新品手动清单最多 10 个不重复 ASIN；表格逐行识别最多 100 个不重复 ASIN。后端再次校验数量、必填字段、ASIN格式和重复项，不依赖前端限制。
- 老品不再上传单独的“老品数据工作簿”。ASIN 可不填并从广告商品报表识别；填写一个或多个 ASIN 时只处理指定对象。识别超过 100 个 ASIN 时必须人工指定，防止误跑超大任务。
- 开始日和结束日不再人工输入，由 Python 从上传报表日期列自动识别。
- 任务仍兼容项目目录、`Downloads`、`Documents`、`Desktop` 中的合法本机路径，但普通网页操作不再要求用户填写路径。
- 任务记录保存在 `runtime/operator-jobs/`，该目录不进入 Git。
- 后台只监听 `127.0.0.1:8766`，网页只在本机访问。
- Codex 使用只读沙箱，输出必须通过 `operator-result.schema.json` 和独立 Validator。
- 仅允许 `rug`；不会连接或操作 Amazon 后台；所有建议都需要人工确认。

## 老品两步操作

1. 把亚马逊或广告系统导出的搜索词、投放对象、广告位、广告商品、Campaign/Ad Group 设置等原始报表一次上传、拖入或选择整个文件夹，然后点击“聚合数据报表”。这一步只运行本地 Python，不调用 Codex。
2. 聚合成功后检查 ASIN、日期和结果文件，再点击“生成 SP 广告优化方案”。这一步复用已经生成的数据包，不重复聚合，之后才调用 Codex 和独立 Validator。Validator 通过后输出《SP广告优化方案.xlsx》。

完整的 7/14/30 天成套报表走 `REPORT_ONLY_OVERLAP_SAFE_MULTI_ASIN`：30 天每日明细是事实基线，7/14 天及汇总表只校验，不重复相加。缺 Amazon 不可变 ID 时可生成分析包，但执行权限继续阻断。
