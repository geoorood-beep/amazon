# Rug 候选阈值自动累积与提醒

## 数据从哪里读

本地监控只读取：

```text
<项目根目录>/imports/threshold-calibration/*.csv
```

每个文件必须是日粒度，字段见[阈值校准合同](../../contracts/threshold-calibration.md)和[CSV 示例](../../config/threshold_calibration_samples.example.csv)。程序读取目录中的全部 CSV，以 `Segment + 日期 + 对象粒度 + 对象ID + 策略阶段` 去重；发现重复时整批阻断，不会把 7/14/30 天重叠数据重复累计。

当前不会登录 Amazon，也不会从 Seller Central 自动下载。用户导出报表并完成日粒度标准化后，只要新 CSV 落入该目录，下一次监控就会重新计算累计样本。现有六表聚合工具负责报表去重和确定性聚合；阈值校准仍要求额外补齐 Rug 类型、尺寸档、策略阶段、归因成熟和验证窗口等校准字段。

## 是否需要云存储

不需要。第一阶段的历史 CSV、候选包、SHA-256 和提醒状态都保存在本机，数据不必上传云端。

以下情况才需要外部服务：

- 电脑关闭时仍要持续运行；
- 需要系统自动从 Amazon Ads API 拉取新报表；
- 多台电脑或多人需要共享同一历史库；
- 需要飞书、邮件或其他渠道推送。

这些能力需要真实 API/MCP/服务器连接器和凭据管理；当前第 05 层外部网关仍为 `PLACEHOLDER_NOT_ACTIVE`。

## 自动判断与提醒

默认调度固定为每周一 `09:00`，使用安装设备本地时区。该默认值保存在[阈值监控配置](../../config/threshold_monitoring.json)，复制到其他电脑或重新安装智能体时也应沿用；不得默认创建每日检查。同一项目只允许一个活动监控。

监控执行：

```bash
.venv/bin/python scripts/monitor_threshold_candidates.py
```

它会重新读取全部历史 CSV，并按[资格阈值正文](../../thresholds/rug/calibration-eligibility.md)判断：

- `2,000 点击 + 50 广告订单 + 14 日`：参考候选；
- `5,000 点击 + 100 广告订单 + 30 日 + 3 窗口`：较高置信候选；
- `300 点击 + 0 订单 + 14 日`：零订单风险候选，只提示风险，不生成正式性能阈值。

相同 Candidate ID 只提醒一次。候选包或数据来源变化时 Candidate ID 会变化，可以再次提醒。提醒完成后由监控任务登记：

```bash
.venv/bin/python scripts/monitor_threshold_candidates.py \
  --mark-notified "THRCAND-..."
```

## 未来迁移到云端

云存储和云端定时任务已经保留[接入位](../../integrations/cloud/threshold-monitoring-cloud-slot.md)，当前状态为 `PLACEHOLDER_NOT_ACTIVE`。未来提供 Provider、Bucket/Container、账户范围和凭据环境后，可把同一脚本部署为每周云端任务。

迁移时本地 Heartbeat 与云端 Scheduler 必须互斥，只能启用一个；云端输入保持只读，先校验对象版本、SHA-256、重复粒度和 Rug 类目，再运行同一候选生成与证明程序。云端化不会获得正式阈值写入权或 Amazon 执行权。

## “更好”的证据边界

程序自动计算 CVR 的 Wilson 95% 区间和日粒度 P25/P50/P75。对 `SKU_SIZE` 粒度，它只用前 70% 日期和至少 7 个对象生成候选四档边界；后 30% 日期完全留出，不参与拟合。

在至少 20 个可评估对象和 100 对可比较对象对上，程序并排检查当前阈值与候选阈值对留出期 CVR、CPA、ACOS 的分层一致率，并做 1,000 次对象级 Bootstrap。单项一致率至少提高 5 个百分点且 95% 区间下界大于 0 才记为 `BETTER`；至少两项 `BETTER` 且没有 `WORSE`，才输出 `HISTORICALLY_BETTER_CANDIDATE`。

Target、搜索词、Campaign 等粒度不能拿来证明当前 `SKU_SIZE` 性能阈值更优，只会输出粒度不匹配。证据不足输出 `INCONCLUSIVE`，历史反向验证变差输出 `NOT_BETTER`。

`HISTORICALLY_BETTER_CANDIDATE` 证明的是未参与拟合的历史留出期中分层能力显著更强，不是未来因果收益保证。结果仍需人工批准、回归和上线后复盘；程序永远不直接覆盖正式阈值。
